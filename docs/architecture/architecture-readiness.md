## Архитектурно значимые требования

R1 — обязательное по постановке: внешнее API из Python, исходный код проверяем, запуск воспроизводим. R2 — подтверждённое заказчиком в комментарии ограничение: один эпизод и одна активная запись; новая после завершения по отдельной просьбе. R3 — общий проектный инвариант из Brief/UX (предварительное требование Discovery до приёмки): авторство пользователя, нейтральная помощь, спорное отдельно, нет диагностики. R4 — проектные правила: частичная запись при определённом эпизоде, явное подтверждение актуального итога, отдельная правка/пропуск, подтверждённая отмена. R5 — проектные правила: фактическое сохранение, успех только после операции, повтор без дубликата (TC-08); остановка при непосредственной угрозе (TC-15). R6 — ограничения безопасности из Brief и DISC-004: синтетические публичные примеры, запрет приписывать переживания, немедленная остановка упражнения при явной угрозе. Рассматриваются как обязательные ограничения предлагаемой архитектуры, но это не клиническая валидация. R7 — постановка: ручные тесты ключевых сценариев, доказательства скриншотами/видео; проверяемость кода. R8 — дедлайн 7 декабря; другие интерфейсы разрешены; стенд желателен, не требование публичной доступности. R9 — H-01–05 остаются открытыми гипотезами; A/B/C — альтернативы, а не утверждённые требования.

## Минимальные решения заказчика

1. Q08: какой UX входит в MVP после отчётов команды? Зафиксировать вариант, основания и условия пересмотра в Issue #1. Без ответа нельзя планировать сценарий.
2. Q09: учебная демонстрация только на синтетике, локально/закрыто, или допускаются личные записи и несколько пользователей? Нужна ли долговременность, кто имеет доступ, когда удаляются данные и можно ли возобновить работу после остановки? Без ответа не выбирать эксплуатационный режим. Для реальных данных необходима отдельная проверка применимых правил и политики сервисов.
3. Q07: какие API-ключи/бюджет/ограничения доступа доступны команде? Не публиковать ключи. После списка сравнить документированные возможности и провести минимальный синтетический smoke-test.

Навыки/доступная площадка уточняются у команды для Q06; численные SLA не выдумываются. Вариант стенда может быть согласован как локальная демонстрация, если закрытый хост недоступен. Голос не считать исключённым окончательно до решения заказчика.

## Формат ADR

[Найгард, Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) — краткая фиксация контекста, решения, статуса, последствий. [MADR](https://adr.github.io/madr/) добавляет сравнение вариантов, критерии и возможность подтверждения. Оба проверены 24.11.2026. Для человеческого выбора подходит адаптированный MADR: локальные последовательные ID, Proposed, отдельная готовность, зависимости, последствия, предложенная проверка и условия пересмотра. Один вопрос — один ADR, без отдельных ADR на обратимые библиотеки. Ссылки на SHA выше.
