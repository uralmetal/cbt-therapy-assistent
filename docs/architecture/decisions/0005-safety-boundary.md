# ADR-0005: Граница остановки обычного сценария при угрозе

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** CONDITIONAL

**Лицо, принимающее решение:** заказчик. **Требования:** R5, R6, R7 ([реестр требований](../architecture-readiness.md)). **Зависимости:** ADR-0001/0002/0003; Q09 для несинтетической эксплуатации.

## Контекст и критерии

Discovery задаёт узкую продуктовую границу: при явном сообщении о непосредственной угрозе себе или другому человеку остановить упражнение до очередного вопроса, структурирования или сохранения. Это не клиническая оценка, кризисная служба или гарантия обнаружения всех угроз. TC-15 и MT-05 — синтетические проверки сценария, не доказательство надёжности детектора. Обязательны приоритет остановки и отсутствие автоматического продолжения; важны обработка сбоя и минимизация ложного доверия.

## Альтернативы

| Вариант | Контроль остановки | Ограничения |
|---|---|---|
| A. Единый промпт одновременно классифицирует, ведёт диалог и сохраняет | Низкий | Модель может продолжить штатный диалог |
| B. Выделенный входной шлюз решения + принудительное состояние остановки в коде | Высокий после сигнала | Ошибки распознавания, дополнительные проверки и задержка |
| C. Полностью ручное подтверждение безопасности перед каждым вводом | Не обнаруживает угрозу в тексте самостоятельно | Утомляет, даёт ложное чувство безопасности |

A не выполняет гарантированный программный переход после обнаружения; C не заменяет обработку явного сообщения.

## Рекомендация архитектора

B только для закрытой синтетической проверки. Сервис хранит safety-состояние отдельно от жизненного цикла записи: Clear (нет неразрешённых safety-входов, не доказательство отсутствия угрозы), Pending (идёт проверка), Unknown (неразрешённые входы без активной проверки либо неразрешимый отказ регистрации), Halted (положительный сигнал, обычный маршрут закрыт). Принятый пользовательский текст, включая текстовую правку/подтверждение, до обычной обработки регистрируется сервисом как отдельный нерешённый safety-вход и инвалидирует прежние разрешения/обычные ответы. Регистрация входа, переходы и разрешение начала Save сериализованы на границе сервиса; UI не является единственной защитой.

### Повторный вход при паузе

Из двух ограниченных подходов (закрыть весь ввод и завершать прогон при запоздалой доставке; проверять каждый принятый дополнительный текст отдельно) предлагается второй: он позволяет учесть поступившую реплику без обязательного завершения демонстрации при обычной задержке. Цена — учёт нескольких нерешённых входов в памяти одной сессии. Это не очередь эпизодов/дневников и не новый клинический функционал.

При Pending/Unknown, а также незавершённом Saving/SaveUncertain интерфейс отключает обычный ввод, кнопки и штатные действия, но постоянно показывает статус паузы и доступную без LLM информацию о срочной местной помощи. Если текст всё же доставлен сервису (гонка отправки, повтор запроса, устаревший UI), применяются следующие правила:

- Каждый новый текст, доставленный в Pending/Unknown или Saving/SaveUncertain, регистрируется как safety-only до обработки результатов других проверок, получает собственный ID, исходный текст и статус. Не помещается в поля, кандидаты, историю или очередь следующей записи СМЭР. Пользователь видит, что текст принят только для проверки, не для дневника. Точный повтор того же ID и текста не создаёт новый вход; изменение текста под старым ID считается новым нерешённым входом, а не отрицательным результатом старого. Запросы к шлюзу используют идентификатор входа и отдельный токен актуальной попытки.
- Проверки сериализованы, не более одной активной на сессию. При завершении/тайм-ауте текущей попытки проверяется следующий ещё не проверенный принятый вход. Unknown прежнего входа сохраняется и не мешает проверить последующий. При исчерпанной очереди без активной проверки и наличии нерешённых входов — Unknown; пользователь может повторить проверку нерешённых входов, каждый с новым токеном, без бесконечных автоматических повторов. Если шлюз недоступен, непроверенный вход остаётся нерешённым; отсутствие результата не считается отрицанием угрозы. Локальное правило может помочь распознать явный сигнал, но не обязательно и не заменяет учёт нерешённых входов.
- Действительный результат закрывает только соответствующий вход. Любой действительный положительный → Halted немедленно, остальные проверки прекращаются, прежние разрешения аннулированы; текущий дневник не продолжается. Clear возможен только когда все принятые входы этой паузы имеют действительный отрицательный результат, нет активных/ожидающих/неизвестных проверок и нет неразрешённого отказа регистрации. Поздний/устаревший ответ не меняет состояние. При ограничении ресурсов не терять нерешённость: если доставленный текст невозможно зарегистрировать, атомарно зафиксировать неразрешимый отказ приёма (Unknown с признаком запрета возобновления; если другая проверка ещё идёт, Pending до её завершения), заблокировать обычный маршрут до завершения прогона по Q09, показать статическую помощь и сообщить, что текст не принят/не проверен. Не обещать его сохранность или восстановление. Пределы памяти и тайм-ауты определяются при реализации, без утверждения численных требований.
- После Clear первичный штатный ввод остаётся в живой сессии для обработки при актуальном контексте; если дополнительный вход инвалидировал первоначальное разрешение, до любого обычного действия с карточкой нужна новая явная команда продолжить обработку исходного ввода либо явно отказаться от него. Не применять старый ответ LLM и не выполнять ранее ожидавший Save автоматически; Save возможен только по новому явному подтверждению актуальной версии и при соблюдении ADR-0002/0004. Safety-only текст не переносится в дневник даже после отрицательного результата; при необходимости человек отдельно отправляет его заново как штатный ввод. При Halted новые обычные входы не принимаются, доступна только статическая помощь/выход и read-only сверка уже начатой операции.

### Приоритет и границы

Все обычные действия (включая Save/Edit/Skip/Cancel/New, обычный повтор, поздний ответ, отправку очередного вопроса) требуют Clear, актуального поколения, версии и допустимого жизненного цикла. Pending/Unknown/Halted и отказ регистрации блокируют их. При ожидании/недоступности доступны статическое сообщение о паузе и информация о срочной помощи без утверждения наличия/отсутствия угрозы, повтор нерешённых safety-проверок, выход без утверждения отмены/успеха. При Halted статический ответ: «Сейчас важна срочная помощь. Обратись в местную экстренную службу и, если можешь, позови человека рядом. Этот чат не оказывает экстренную помощь или психотерапию». Не передавать сообщения третьим лицам автоматически. Возобновление после Halted/отказа регистрации или потери сессии, удаление и межсессионная политика — Q09; в текущем прогоне нет штатного выхода из этих блокировок.

Перед началом транзакции снова проверяется Clear. Уже начатая операция может завершиться; read-only сверка не снимает safety-блокировку, статус commit не заменяет сообщение о помощи, отмена задним числом не обещается. Safety-only тексты и минимальные метаданные проверки удерживаются лишь в живой сессии, не попадают в БД дневника, обычный LLM-контекст, публичные материалы или логи. После разрешения/остановки больше не нужны для обычного маршрута; политика жизненного цикла, включая незавершённые проверки, — Q09. Q07/Q09 определяют допустимость и доступность обоих видов LLM-вызова, для обоих минимизация контекста.

Уверенность средняя в контроле переходов, низкая в детекции. Дополнительный вход не гарантирует выявление угрозы, отрицательный результат не клиническое заключение. Реальные данные и открытая эксплуатация не разрешены этим предложением.

## Последствия и проверка

Дополнительный шаг повышает задержку, может останавливать допустимые запросы. Прогнать MT-05/TC-15 на входе, в активной записи и перед подтверждением, включая отказ API, ложноположительный синтетический пример и попытку обойти остановку. Критерий: после обнаружения явного сигнала ни раскладки, ни вопроса СМЭР, ни сохранения; сбой не трактуется как отрицательный сигнал. Измерять пропуски и ложные срабатывания отдельно; результат теста не подтверждает клиническую безопасность.

Дополнительные отрицательные проверки: Review → Pending/Unknown → Save/Edit/Skip/Cancel/New/обычный повтор/поздний ответ — запрещены; устаревший отрицательный ответ не снимает блокировку; действительный результат текущей проверки разрешает только допустимый переход. Halted — статическая помощь без внешней LLM, нет нового Save. Read-only сверка факта уже начатого commit не разрешает упражнение; не обещать отмену ранее совершённой операции.

Дополнительные проверки ARCH-R-005: отдельные Pending и Unknown с доставленным B, недоступным шлюзом и последующим отрицательным результатом A; B не закрыт и Save/обычный ответ запрещены. Проверить B → положительный (Halted), B → действительный отрицательный при всех остальных отрицательных (Clear), неизвестность A при отрицательном B, повтор токена/ID, невозможность регистрации, отсутствие B в записи/обычном LLM-контексте и отсутствие автоматического Save после Clear. См. [W12–W19](../architecture-review.md#повторная-проверка-архитектурных-маршрутов).
