# ADR-0006: Интерфейс учебной демонстрации

**Статус:** Accepted · **Дата:** 2026-11-24 · **Готовность:** CONDITIONAL

**Лицо, принимающее решение:** заказчик. **Требования:** R1–R8, R10–R12 ([Readiness](../architecture-readiness.md)). **Зависимости:** ADR-0001/0002/0004/0005; Q08/Q09.

## Контекст и критерии

[Заказчик](https://github.com/uralmetal/cbt-therapy-assistent/pull/3#discussion_r4677150230) просит рассмотреть Telegram + Python backend как простой и понятный вариант. Telegram принят заказчиком; UX-A/B/C и голос отдельно от выбора канала. Нужны свободный текст/пошаговый ввод, видимая карточка, правка, пропуск, подтверждение, отмена, безопасность и воспроизводимость. Python на Render, stateless, до 10 пользователей, меньше 1 входящего запроса/с.

## Альтернативы

| Вариант | Разработка и UX | Ограничения |
|---|---|---|
| Telegram Bot API + Python backend | Нативный чат, кнопки, текст, не нужен отдельный frontend; удобная демонстрация преподавателю | Нет полного контроля ввода/формы, внешняя доставка, повторы/устаревшие кнопки, не secret chat; требуется доступ к Telegram |
| Python web UI (например Streamlit) | Чат и редактируемая карточка с контролируемыми полями, браузер | Внешнее состояние обязательно, Session State не источник истины; собственный контроль доступа |
| Jupyter Notebook + виджеты | Удобный воспроизводимый учебный клиент | Не основное размещённое на Render приложение; пригоден как демонстрационный/тестовый клиент при том же ядре |
| SPA + Python API | Максимальный контроль интерфейса и правок | Два компонента, больше затрат; нет драйвера для MVP |

## Рекомендация архитектора

Telegram — выбранный интерфейс текстового MVP с UX‑A. Для живого прогона требуется допуск Q09: приватный чат с ботом (не групповой/inline), allowlist до 10 тестовых пользователей как предложенный контроль синтетического режима; идентифицировать авторизованного отправителя по Bot API user_id и chat_id, сопоставлять с внутренним псевдонимом, не по username; не использовать ID в аналитике. Не E2E secret chat: сообщения доступны платформе и разработчику бота согласно [Telegram Privacy](https://telegram.org/privacy) и [Bot privacy policy](https://telegram.org/privacy-tpa). Для реальных данных — отдельное решение и проверка условий, доступа, удаления у всех посредников.

Webhook на Render с HTTPS, проверка X-Telegram-Bot-Api-Secret-Token, разрешённых типов обновлений/отправителей, серверная проверка актуального действия и версии. update_id вместе с отпечатком содержимого — ключ дедупликации точного дубля в БД; отличающееся содержимое под тем же ID учитывается как отдельный нерешённый safety-вход по ADR-0005 (или явный отказ с блокировкой), не гарантия доставки/порядка; max_connections=1 как простая настройка-кандидат, не единственная защита; при сетевых повторах/рестарте использовать устойчивый inbox, не полагаться на UI или память. Callback содержит непрозрачную ссылку на действие/версию, не содержимое записи; чужие, просроченные и повторные кнопки проверяются на сервере. Успех только после commit; повтор ответа не создаёт вторую запись. Нельзя гарантировать exactly-once доставку ответов Telegram, различать факт записи и факт доставки сообщения. При холодном старте и ошибке доставки — явный статус/команда проверки, не повторное сохранение. Принятые входы — зарегистрированные в БД, не просто видимые в клиенте Telegram.

Пользователь видит итоговую карточку и явные действия «Изменить», «Пропустить», «Сохранить», «Отменить»; пользовательское уточнение без автоматического принятия кандидатов. По [резолюции заказчика](../../product/hypotheses-and-options.md#итоговое-решение-заказчика--26112026) реализуется UX‑A. Правила пошагового и короткого маршрутов описаны в [спецификации](../../product/interaction-spec.md). Голос отложен по Q10. При Pending/Unknown/SaveUncertain бот **не может технически отключить отправку нового текста клиентом Telegram**: удаляет/обесценивает прежние кнопки насколько возможно, показывает статус и статическую помощь, все обычные команды сервер отклоняет. Уже доставленный свободный текст учитывается как safety-only согласно ADR-0005, не как следующая запись. Повтор safety и сверка — отдельные команды; после Clear не применять старый Save. При Halted обычный маршрут закрыт, только помощь/выход и read-only сверка уже начатого commit. Если БД недоступна, не ACK как успешный приём/сохранение, помощь без LLM при возможности доставки; после восстановления сверка устойчивых входов.

Уверенность средняя: Telegram удобен для чатового формата, но нужно проверить видимость спорных фрагментов, корректировку карточки, время холодного старта, доступ преподавателя и условия обработки. Если тесты правок/подтверждения или условия данных делают канал непригодным, предложить заказчику пересмотр в пользу web UI; не менять автоматически.

## Последствия и проверка

MT-01–05 на выбранном UX, скриншоты/видео только с синтетикой, отдельные пользователи, старые callback, повтор webhook, перестановка доставки, safety-only текст при паузе, рестарт Render и доступ к статической помощи. Проверить авторизацию и доступ преподавателя, инструкцию локального воспроизводимого запуска с внешним тестовым хранилищем; никаких локальных пользовательских записей. [Telegram Bot API](https://core.telegram.org/bots/api), [FAQ](https://core.telegram.org/bots/faq), [Streamlit Session State](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state), [Render Free](https://render.com/docs/free) — проверены 24.11.2026.

## Решение заказчика

24.11.2026 · [Комментарий](https://github.com/uralmetal/cbt-therapy-assistent/pull/3#discussion_r4677587205) на HEAD `a1b6d2ee01ea71ea8ef8432989c22297a52e0f34`.

Принят Telegram Bot API как интерфейс текстового MVP. На дату этого решения выбор UX относился к Q08. 26 ноября заказчик выбрал UX‑A. Голос отложен по Q10. Не принимаем автоматически конкретный SDK, FastAPI или тариф; ограничения Telegram и допуск Q09 остаются.

Принятие решения не равно готовности реализации. Условия, проверки и открытые вопросы остаются в силе; фактические тесты не выполнены.
