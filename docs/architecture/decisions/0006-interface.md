# ADR-0006: Интерфейс учебной демонстрации

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** CONDITIONAL

**Лицо, принимающее решение:** заказчик. **Требования:** R1, R2, R3, R7, R8 ([реестр требований](../architecture-readiness.md)). **Зависимости:** ADR-0001/0002; Q08, Q09.

## Контекст и критерии

Учебное задание допускает альтернативу Notebook; необходимы видимые сценарии и воспроизводимый запуск. Выбор UX-A/B/C открыт, голос — гипотеза H-05. Требуется показать версию карточки, правку, пропуск, отмену и подтверждение. Выбор технологии не определяет предпочтительный UX. Навыки команды и доступная инфраструктура не подтверждены.

## Альтернативы

| Вариант | UX и проверка | Стоимость реализации (качественно) | Ограничения |
|---|---|---|---|
| A. Jupyter Notebook + виджеты | Возможен пошаговый демонстрационный интерфейс | Низкая, если знаком команде | Неудобная имитация чата и управление повторным исполнением |
| B. Python веб-интерфейс (например Streamlit) | Чат и редактируемая карточка; наглядные ручные тесты | Низкая–средняя при знакомстве | Перезапуски UI, ограничения кастомизации и жизненного цикла сессии |
| C. Отдельный SPA + Python backend | Максимальный контроль над UX | Выше, два приложения/контракта | Оправдано при сложных требованиях к UI или компетенциях команды |

Все варианты потенциально удовлетворяют учебному заданию; простой notebook с print без механизма контроля состояния — недостаточная демонстрация.

## Рекомендация архитектора

B при подтверждении текстового UX и наличии навыков команды: минимальный Python web UI, Streamlit — кандидат, не утверждённый стек. Ядро отдельно от UI, интерфейс отображает только проверенное состояние, явные действия и карточку; для A задаёт пошаговые вопросы, для B/C показывает кандидатные фрагменты отдельно. Реализуется только выбранный заказчиком UX; возможность подмены стратегии не означает обязательную реализацию трёх вариантов. Streamlit Session State сохраняет значения между повторными исполнениями в рамках пользовательской сессии, но привязан к соединению WebSocket и может сбрасываться; поэтому не использовать его как долговременное хранилище. Изоляция проверяется отдельно. Демонстрационный профиль ограничен одной контролируемой живой сессией/вкладкой (ADR-0002); вторая вкладка/переподключение не гарантируют восстановление или глобальную уникальность и не считаются обходом запретов. Расширение профиля требует Q09 до выпуска. UI не обходит SaveUncertain и Pending/Unknown/Halted через rerun или кнопки. Если команда быстрее реализует Notebook, а сценарии доступны для ручной демонстрации, A становится предпочтительным. Если необходим сложный UI/независимый клиент — C и повторное рассмотрение ADR-0001.

Уверенность средняя. Никакого публичного размещения чувствительных данных. Стенд по возможности ограничить доступом; при отсутствии безопасного стенда демонстрировать локально и зафиксировать ограничение.

## Последствия и проверка

Удобная демонстрация без отдельного frontend; возможны ограничения обновления страницы, редактирования и нескольких сессий. Проверка MT-01–05 на выбранном UX, включая раздельные сессии, повторное исполнение UI и явное сохранение; результат подтверждается синтетическими скриншотами/видео. Чистый запуск преподавателем по инструкции и проверка внешнего API обязательны согласно текущей постановке. Невозможность воспроизвести переходы — повод сменить UI, а не ослабить бизнес-инварианты.

Отрицательные тесты UI: Save/Edit/Cancel/New при SaveUncertain, Save/Edit/Skip/Cancel/New/обычный повтор при safety-блокировке, переподключение и вторая вкладка как граница применимости, а не доказательство глобальной уникальности.

По ARCH-R-005: при Pending/Unknown и Saving/SaveUncertain UI отключает штатный текстовый ввод и обычные команды, показывает статус паузы, безопасный выход, повтор нерешённых проверок и статическую информацию о срочной помощи без LLM. Если запрос успел поступить на сервис, UI показывает результат регистрации как safety-only или явный отказ приёма; не выдаёт его за запись СМЭР или отрицательную проверку. Сервис отдельно учитывает каждый доставленный вход, поэтому UI не может объявить Clear по одному ответу; после разрешения всех входов требуется актуальное явное действие, а не автоматическое исполнение старого Save. При отказе регистрации/Halted обычный маршрут закрыт до завершения прогона, политика Q09. Проверить гонку отправки, недоступность шлюза, поздний результат A при нерешённом B и отсутствие B в карточке (ADR-0005, W12–W19).
