# ADR-0004: Хранение подтверждённых записей учебного MVP

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** CONDITIONAL

**Лицо, принимающее решение:** заказчик. **Требования:** R2, R4, R5, R7, R8 ([реестр требований](../architecture-readiness.md)). **Зависимости:** ADR-0001/0002; допуск реальных данных и идентификация Q09.

## Контекст и критерии

Сохранение должно быть реальной операцией приложения, а не текстовым обещанием. История, восстановление после перезапуска, многопользовательское хранение и сроки удаления не согласованы. Для учебной конфигурации рассматривается явно ограниченное допущение: локальный либо закрытый изолированный запуск на синтетических эпизодах; хранение итоговой записи после сохранения и перезапуска является предложением архитектора, не новым обязательным продуктовым требованием.

## Альтернативы

| Вариант | Целостность/повторы | Развёртывание | Ограничения |
|---|---|---|---|
| A. Только память процесса | Можно обеспечить внутри процесса | Самое простое | Перезапуск теряет результат; не годится при требовании долговременности |
| B. SQLite на локальном диске | Транзакции, уникальность операции | Один файл, без отдельного сервера | Нужен доступный постоянный диск; нет встроенного разграничения пользователей приложения |
| C. Отдельная управляемая реляционная БД | Транзакции, возможности многопользовательской эксплуатации | Дополнительная служба и секреты | Стоимость, администрирование, география и политика хранения |

A приемлем, только если заказчик допускает сохранение на время сессии. C не требуется без подтверждения удалённого долговременного или многопользовательского хранения.

## Рекомендация архитектора

B для синтетической демонстрации при постоянном диске. Хранить подтверждённые поля и минимальные технические метаданные операции, не полный диалог, кандидатов, аудио или содержимое логов. Черновик — в живой сессии; восстановления после рестарта не обещаем. Атомарная запись и уникальный ID попытки неизменно связаны с эпизодом, версией и снимком подтверждённой карточки. Несовпадение ID и снимка отклоняется.

Три исхода: подтверждённый commit → Saved; доказанный неуспех, исключающий поздний commit → Review; неопределённый исход → SaveUncertain. Неизвестность не откат. Снимок и ID заморожены, допустима только read-only сверка этой попытки, без нового Save/правки/отмены/нового эпизода. Сверка авторитетно устанавливает commit с тем же снимком либо отсутствие записи при завершённой/невозможной поздней операции. Ошибка чтения и отсутствие строки при ещё возможном commit оставляют SaveUncertain. После подтверждения commit — Saved исходной версии, не открывать новую автоматически; после доказанного неуспеха — Review, повтор того же снимка с прежним ID, новый ID только после правки и нового подтверждения; отмена лишь после доказанного неуспеха. Все обычные действия требуют Clear (ADR-0005). Safety-блокировка во время операции разрешает read-only сверку факта уже начатой записи, но не новый Save/обычное продолжение; нельзя обещать отменить commit задним числом.

Если диск непостоянный — согласованный временный режим с предупреждением или внешняя БД после Q09. Потеря сессии при неизвестном исходе не равна отмене, продолжение не гарантировано; восстановление и сверка между сессиями — Q09. Уверенность средняя: режим данных/долговременность не утверждены. При реальных данных/нескольких пользователях определить доступ, жизненный цикл, удаление, допустимые сервисы и пересмотреть B/C. SQLite не обеспечивает конфиденциальность сама по себе.

## Последствия и проверка

Плюс — простая локальная проверка реального сохранения без инфраструктуры. Минус — ограничения при размещении и конкурентном доступе. Проверить TC-08, MT-01/03/04, перезапуск процесса для сохранённой синтетической карточки, тайм-аут после коммита, повтор идентификатора и отмену. Критерий: одна запись после повторного запроса, отменённой записи нет, исходный диалог не попадает в хранилище. Запрет реальных данных на учебном стенде не заменяет контроль доступа (Q09).

Отрицательные тесты: commit с потерянным ответом и неисполненный commit отдельно; Save/Edit/Cancel/New до сверки запрещены; отсутствие строки при возможном позднем commit не разрешает Review. После сверки корректный Saved/Review, повтор того же снимка без дубля; проверить safety-блокировку во время сверки. Отменённой записи нет только при подтверждённой отмене до commit/после доказанного неуспеха.
