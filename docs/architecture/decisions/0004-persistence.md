# ADR-0004: Внешнее хранилище состояния и записей

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** CONDITIONAL

**Лицо, принимающее решение:** заказчик. **Требования:** R2–R8, R10–R12, R14 ([Readiness](../architecture-readiness.md)). **Зависимости:** ADR-0001/0002/0005; Q09 режим данных и доступ; Q11 выбор сервиса.

## Контекст и критерии

[Требование заказчика](https://github.com/uralmetal/cbt-therapy-assistent/pull/3#discussion_r4677213364): никакого локального хранилища, Python строго stateless. Нужны простота для небольшой команды и независимая аналитика LLM. Google Sheets и Airtable — кандидаты, не принятые решения. Требуются сохранение инвариантов (один активный эпизод, версия, safety, повтор без дубликата), изоляция до 10 пользователей, устойчивость к рестарту Render, понятный доступ для аналитики и низкая цена. Локальный SQLite/память исключены как источник истины. Обзор официальных тарифов и API — 24.11.2026, доступ к аккаунтам и фактическая нагрузка не проверены.

## Нагрузка и стоимость

RPS недостаточно для расчёта квоты. Иллюстрация, не прогноз: 10 человек × 1 эпизод/день × 8 входов/эпизод × 30 дней = 2 400 входов/мес. Даже один Airtable API-вызов на вход превышает 1 000; несколько чтений/записей и аналитика ухудшают ситуацию. Для Sheets сервисный аккаунт расходует общую минутную квоту; при входном потоке 0,9/с и 2 записывающих вызовах на вход ≈108 записей/мин, выше 60. У Postgres объём этих данных мал, но CU-hours зависят от времени активности/подключений, паузы и рестарты проверяются отдельно. Не обещаем бесплатность; измерить фактические запросы, размеры данных и активность, установить лимиты.

## Рекомендация архитектора

Supabase PostgreSQL Free как первый кандидат для согласованной синтетической демонстрации, Neon — запасной. Один внешний Postgres и серверный Python-адаптер (SQL/psycopg либо другой Python-драйвер, не утверждённая библиотека). Преимущество Supabase — табличный просмотр и SQL для независимой аналитики при сохранении атомарности. Airtable/Sheets оставить возможным ручным/контролируемым экспортом подтверждённой синтетики, **не** обязательной интеграцией и не вторым источником истины. Не синхронизировать сырой диалог; аналитика получает read-only SQL-представление/CSV из разрешённых подтверждённых записей с псевдонимом или агрегатами. Аналитическая роль не видит черновики, safety-only, секреты и реальный идентификатор Telegram; запись из LLM/аналитики запрещена. Если захотим удобный просмотр через Airtable/Sheets, экспорт по явному разрешению, без автоматического дублирования/передачи личных данных. Это предложение, не выбор заказчика.

**Два набора данных в одной БД:** (1) оперативное ограниченное состояние — псевдоним пользователя/сессии, активный эпизод, версия, черновик/минимальные исходные фрагменты для происхождения, кандидаты, отдельные нерешённые safety-входы и их токены/статусы, durable inbox с уникальным ID входа, immutable Save-попытка, состояние обработки и срок жизни; (2) подтверждённая карточка и минимальный ID операции/версии. Нет постоянного архива полного диалога, исходных аудио или safety-only в дневнике; закрытые оперативные данные не являются аналитическим набором. Сроки хранения, минимизация, очистка, правомерность передачи и доступ — Q09; нельзя очищать нерешённые блокировки так, чтобы получить Clear/новый эпизод, срок истёк → запрет возобновления до согласованной процедуры. При Halted не хранить дополнительный текст без необходимости; факт блокировки должен пережить рестарт. Для реальных данных выпуск заблокирован.

**Конкуренция и сбои.** Все изменения состояния и регистрация входа сериализуются по субъекту в БД (транзакция с блокировкой строки либо эквивалентной проверкой версии; уникальные ключи для одного активного эпизода/входа/попытки, транспортный ID вместе с отпечатком содержимого для отличения точного дубля от изменённого текста). Состояние и факт приёма входа фиксируются до ACK. Внешние LLM-вызовы не внутри долгой транзакции; claim/lease с токеном поколения записан в БД, поздний ответ сравнивается при применении, истёкший claim не снимает неопределённость. Повтор запроса после рестарта восстанавливает состояние из БД; нерешённые входы остаются Pending/Unknown, не Clear. Не подтверждать Telegram webhook при неопределённом приёме; повтор с тем же update_id сначала сверяет запись. При недоступной БД не выполнять обычный маршрут/Save и не выдавать факт приёма/успеха; статическая помощь доступна насколько доставляем канал, не зависеть от LLM. Обычные действия допускаются только после чтения авторитетного состояния; гарантия относится к принятым (durably recorded) входам, не к сообщениям, ещё не доставленным Telegram. Не обещать глобальную последовательность доставки.

**Сохранение.** ID попытки неизменно связан с пользователем/эпизодом/версией/снимком. До записи карточки в короткой транзакции фиксируется намерение с ID, снимком, актуальным подтверждением и Saving; неопределённый исход регистрации намерения сначала сверяется, без новой попытки. В отдельной транзакции записи под той же блокировкой субъекта повторно проверяются Clear, разрешение поколения и актуальная версия; карточка и Saved фиксируются атомарно с уникальным ключом. Рестарт между двумя транзакциями не разрешает автоматический Save: сначала сверка попытки, доказательство отсутствия commit и невозможности поздней записи (в том числе аннулирование старого токена/права на запись под блокировкой), затем Review и новое явное подтверждение при Clear. Если safety-вход принят между регистрацией намерения и записью карточки, проверка при записи не позволяет выполнить устаревший Save. Три исхода: подтверждённый commit → Saved; доказанный неуспех, исключающий поздний commit → Review; неизвестность → SaveUncertain, конфликтующие Save/Edit/Cancel/New запрещены, только авторитетная сверка того же ID/снимка. При рестарте факт попытки и состояние сохраняются. Отсутствие строки при ещё возможном commit/неизвестности не разрешает Review. После доказанного неуспеха повтор неизменённой версии с тем же ID; новая версия требует нового подтверждения. Сверка уже начатой операции не снимает safety-блокировку, commit не отменяется задним числом. При одновременном новом входе и Save порядок определяется транзакционной границей: принятый раньше вход блокирует начало Save; уже завершённый commit нельзя отменить.

## Последствия и проверка

Дополнительная внешняя БД и настройка доступа; меньше самописной координации. До выбора Q11: создать тестовую БД, проверить доступ из Render, восстановление после рестарта, уникальность, конкурирующие запросы, неизвестность commit и отсутствие утечки между пользователями, паузу/квоты и read-only экспорт. Проверить TC-08, MT-01/03/04 и W1–W19 с новой границей, сценарии C-W01–C-W10 в review. Не делать вывод об эксплуатации или личных записях по синтетике.

## Решение заказчика

Ожидается согласование рекомендации. Render и stateless без локального хранилища уже заданы заказчиком как ограничения, не как принятие всего ADR. Предлагаемые проверки реализации не выполнены.
