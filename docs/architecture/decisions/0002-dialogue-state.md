# ADR-0002: Управление состоянием и авторством записи

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** READY

**Лицо, принимающее решение:** заказчик. **Требования:** R2, R3, R4, R5, R6 ([реестр требований](../architecture-readiness.md)). **Зависимости:** ADR-0001; определяет требования к ADR-0003/0004/0005.

## Контекст и критерии

Одна активная запись, допустимый частичный итог, отсутствие догадок в сохранённых полях, подтверждение актуальной карточки и запрет смешения эпизодов общи для A/B/C. TC-08 требует восстановления после ошибки без дубля; TC-13/14 различают потерю смысла и происхождение. Точный порядок вопросов и бюджет инициативы зависит от UX. Обязательны предсказуемость переходов и явный пользовательский контроль; желательна независимость от модели.

## Альтернативы

| Вариант | Контроль инвариантов | Сложность | Риск |
|---|---|---|---|
| A. История чата и системный промпт как источник истины | Недостаточен: модель может нарушить правило | Низкая начальная | Неуправляемые повторные записи и догадки |
| B. Явное состояние и переходы в Python, LLM предлагает данные | Проверяемый контроль | Умеренная | Нужно поддерживать версию черновика и переходы |
| C. Полностью жёсткая форма без смысловой обработки | Хороший контроль | Низкая–средняя | Не выполняет свободное структурирование B/C; меньше пользы LLM |

A неприемлем без независимых проверок; C остаётся возможным упрощением при выборе A, если внешний API всё равно решает полезную задачу.

## Рекомендация архитектора

B. Сервис сценария хранит отдельные поля, исходные смысловые единицы на время активной сессии, происхождение (ввод, правка, отдельное принятие предложения), кандидатов вне итоговых полей, выбранные пропуски и версию карточки. Текст модели сам не меняет состояние. Пользовательские действия валидируются; переходы определены кодом. Одна активная запись на изолированную сессию; если нужна глобальная уникальность по человеку, требуется идентификация (Q09). После правки старое подтверждение недействительно. Общая кнопка сохранения не принимает спорные кандидаты. Сохранение только при определённом подтверждённом эпизоде и подтверждении именно показанной версии; повтор той же попытки идемпотентен. После отмены или завершения новая запись открывается лишь отдельным действием. Спорные фрагменты не переносятся в следующий эпизод.

Уверенность высокая в общем механизме; UX-специфичные шаги отложены до Q08. Не предполагается постоянный журнал исходных сообщений.

## Последствия и проверка

Дополнительная модель состояния и правила конкурирующих действий повышают объём кода, но упрощают проверку. Синтетические MT-01–04, TC-08/09/13/14; отдельные отрицательные тесты: старая версия, дублированный запрос, неверный тип, пропажа одной мысли. Успех: неподтверждённый кандидат не сохраняется, вторая запись не открывается, повтор создаёт не более одной записи, ошибка не выдаётся за успех. Семантическую точность и самостоятельность оценивает человек по фактическому вводу; типы данных не доказывают правильность смысла.
