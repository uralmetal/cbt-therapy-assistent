# ADR-0002: Управление состоянием и авторством записи

**Статус:** Accepted · **Дата:** 2026-11-24 · **Готовность:** READY

**Лицо, принимающее решение:** заказчик. **Требования:** R2–R6, R10–R12 ([Readiness](../architecture-readiness.md)). **Зависимости:** ADR-0001/0004/0005; Q09/Q11.

## Контекст и критерии

Общие правила A/B/C: один выбранный эпизод и одна активная запись, частичный итог с триггером, проверяемое происхождение, явное подтверждение версии, отмена и сохранение без дубля. До 10 пользователей, Python строго stateless. Q08 определяет порядок вопросов, не эти правила. Q09 определяет допустимый профиль доступа/данных. READY относится к достаточности общих правил для проектирования, не готовности реализации; выбранное хранилище — ADR-0004.

## Альтернативы

| Вариант | Оценка |
|---|---|
| История чата / промпт / локальная сессия | Нет надёжных инвариантов и восстановления; локальное состояние противоречит R10 |
| Явные переходы в Python + внешнее транзакционное состояние | Проверяемая авторизация, версия, атомарность и восстановление |
| Жёсткая форма без смысловой помощи | Хорошие переходы, но теряет свободный UX B/C; возможна узкая помощь при A |

## Рекомендация архитектора

Второй вариант. Python вычисляет переходы, внешняя БД — единственный авторитетный источник состояния, входных событий и попыток. В живом запросе можно держать заменимые копии; ни UI, ни Telegram, ни RAM процесса не хранят обязательное состояние. Предложенный профиль — контролируемая синтетика с идентификацией/изоляцией до 10 пользователей; при Telegram привязка к авторизованному user_id/chat_id, внутренний псевдоним. Одна активная запись на идентифицированного субъекта в данном приложении независимо от рестарта/повторного входа; не утверждать глобальную уникальность человека между различными аккаунтами или каналами. Нужны согласование Q09 и проверка реальной изоляции; потеря клиента не равна отмене. Новый эпизод не ставится в очередь; открывается отдельной просьбой только после Saved/Cancelled при Clear.

**Авторство.** Сервис проверяет точную цитату и привязку к фактической реплике пользователя выбранного эпизода; правку, отдельное принятие, удаление и пропуск — по реальному действию для актуального кандидата/поля. Самоотчёт LLM не доказательство. Непроверяемое содержимое отдельно либо отклонено, общий Save не принимает кандидатов. Точная цитата не доказывает категорию, смысл проверяет человек; несколько мыслей не теряются без выбранного пропуска. Оперативные фрагменты необходимы для проверки, но не хранятся в постоянном архиве и не доступны аналитике (ADR-0004/Q09). Safety-only не источник поля/кандидат/эпизод.

**Переходы.** Регистрация каждого принятого входа и инвалидация предыдущих разрешений в короткой транзакции по субъекту. Дедупликация update_id/request_id, независимые ID входов, токены попыток, версия/поколение состояния; работа с внешней LLM вне транзакции, результат применяется только если токен/версия/поколение актуальны. Восстановление после рестарта из БД; устаревший claim не закрывает нерешённость, только повтор проверки по новому токену. UI не может обойти Pending/Unknown/Halted или отказ регистрации. Состояние SaveUncertain отделено от safety, read-only сверка не разрешает обычный маршрут. При недоступности хранилища не продолжать, не подтверждать приём, не заявлять сохранение. Гарантии касаются durably принятых входов, не сообщений, ещё не доставленных транспортом.

Save: определённый подтверждённый эпизод, явное подтверждение показанной версии, Clear, актуальное разрешение, нет незавершённой попытки; ID/снимок/версия неизменны; намерение и Saving фиксируются до транзакции карточки (ADR-0004), после рестарта сверка, не автоматический Save. Неизвестность → SaveUncertain, только сверка; доказанный неуспех исключает поздний commit и даёт Review; подтверждённый commit → Saved. При повторе той же версии тот же ID, при новой версии новое подтверждение/ID только после доказанного неуспеха. Отмена возможна до commit либо после доказанного неуспеха при Clear, не отменяет существующую запись. Все изменения одной атомарной границей в ADR-0004.

После дополнительного safety-only ввода до обычных действий требуется разрешение всех входов и новое явное продолжение первичного ввода/отказ; старый Save не выполняется автоматически. Halted/неразрешимый отказ регистрации сохраняют запрет и после рестарта; политика дальнейшего возобновления Q09. 

## Последствия и проверка

Сложнее локальной сессии, но неизбежно при R10. Общие MT-01–04, TC-08/09/13/14, W1–W19 и C-W01–C-W10: старая версия, дубликат, пропажа мысли, два субъекта, конкурентная запись одного, перезапуск при Pending/Unknown/Halted/SaveUncertain, отказ БД, поздний результат, read-only аналитика. При потерянной сессии не начинать новую автоматически. Технические тесты не выполнены.

## Решение заказчика

24.11.2026 · [Комментарий](https://github.com/uralmetal/cbt-therapy-assistent/pull/3#discussion_r4677555132) на HEAD `a1b6d2ee01ea71ea8ef8432989c22297a52e0f34`.

Принят рекомендованный механизм явных переходов Python и внешнего транзакционного состояния. Конкретная БД выбрана в ADR-0004. Граница авторизованного субъекта, версионирование, происхождение и durable safety/Save сохраняются; политика доступа, сроки хранения и восстановление после остановки уточняются Q09.

Принятие решения не равно готовности реализации. Условия, проверки и открытые вопросы остаются в силе; фактические тесты не выполнены.
