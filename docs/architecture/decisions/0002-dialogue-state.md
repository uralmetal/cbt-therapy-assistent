# ADR-0002: Управление состоянием и авторством записи

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** READY

**Лицо, принимающее решение:** заказчик. **Требования:** R2, R3, R4, R5, R6 ([реестр требований](../architecture-readiness.md)). **Зависимости:** ADR-0001; определяет требования к ADR-0003/0004/0005.

## Контекст и критерии

Одна активная запись, допустимый частичный итог, отсутствие догадок в сохранённых полях, подтверждение актуальной карточки и запрет смешения эпизодов общи для A/B/C. TC-08 требует восстановления после ошибки без дубля; TC-13/14 различают потерю смысла и происхождение. Точный порядок вопросов и бюджет инициативы зависит от UX. Обязательны предсказуемость переходов и явный пользовательский контроль; желательна независимость от модели.

## Альтернативы

| Вариант | Контроль инвариантов | Сложность | Риск |
|---|---|---|---|
| A. История чата и системный промпт как источник истины | Недостаточен: модель может нарушить правило | Низкая начальная | Неуправляемые повторные записи и догадки |
| B. Явное состояние и переходы в Python, LLM предлагает данные | Проверяемый контроль | Умеренная | Нужно поддерживать версию черновика и переходы |
| C. Полностью жёсткая форма без смысловой обработки | Хороший контроль | Низкая–средняя | Не выполняет свободное структурирование B/C; меньше пользы LLM |

A неприемлем без независимых проверок; C остаётся возможным упрощением при выборе A, если внешний API всё равно решает полезную задачу.

## Рекомендация архитектора

B. Сервис сценария хранит поля, версию, исходные смысловые единицы и их происхождение на время живой сессии; кандидатов и пропуски — отдельно. Только сервис определяет переходы. Он проверяет привязку цитаты к фактической пользовательской реплике выбранного эпизода (ADR-0003); правку, отдельное принятие, удаление и пропуск — по реальному действию пользователя для актуального поля/кандидата. Метка LLM не доказательство. Непроверяемое содержимое остаётся кандидатом либо отклоняется; общий Save его не принимает. Точная цитата не доказывает верную категорию, смысл проверяет человек. Не терять явно названные мысли без выбранного пропуска.

После правки старое подтверждение недействительно. Save требует определённого подтверждённого эпизода, явного согласия с показанной версией, отсутствия незавершённой попытки и Clear по ADR-0005. ID попытки неизменно связан с эпизодом, версией и снимком подтверждённого итога. Доказанный неуспех → Review; неизвестный исход → SaveUncertain: замороженный снимок, запрещены Save/правка/отмена/новая запись, только сверка этой попытки. Commit подтверждён → Saved той же версии; доказано отсутствие commit и невозможность позднего завершения → Review. Отсутствие строки при ещё возможном commit не доказывает неуспех. После доказанного неуспеха повтор той же версии использует исходный ID; правка и новое явное подтверждение позволяют новый ID. Отмена допустима только при отсутствии незавершённой попытки и Clear. После Saved/Cancelled новая запись открывается отдельной просьбой, без очереди; второй эпизод не смешивается с текущим.

Предложенный синтетический демонстрационный профиль — одна контролируемая живая сессия, одна вкладка/экземпляр UI. READY касается общего механизма, не глобальной уникальности по человеку. Вторая вкладка/переподключение не гарантируют восстановление и не являются способом обхода запретов; потеря сессии с неизвестным исходом или остановкой завершает текущий прогон, не означает отмену, дальнейшая сверка/возобновление — Q09. Если нужны несколько вкладок/пользователей, до выпуска решить Q09 и перепроверить механизм. Это условие предложения, не принятое продуктовое решение.

Уверенность высокая в механизме при этих границах. UX-специфичные шаги — Q08. Safety-блокировка имеет приоритет над обычными переходами и не снимается результатом сверки. Постоянный журнал диалога не предполагается.

## Последствия и проверка

Дополнительная модель состояния и правила конкурирующих действий повышают объём кода, но упрощают проверку. Синтетические MT-01–04, TC-08/09/13/14; отдельные отрицательные тесты: старая версия, дублированный запрос, неверный тип, пропажа одной мысли. Успех: неподтверждённый кандидат не сохраняется, вторая запись не открывается, повтор создаёт не более одной записи, ошибка не выдаётся за успех. Семантическую точность и самостоятельность оценивает человек по фактическому вводу; типы данных не доказывают правильность смысла.

Дополнительные отрицательные проверки: неизвестный исход при Save/Edit/Cancel/New, ложная метка происхождения, чужой эпизод, кнопки при Pending/Unknown/Halted, две вкладки/переподключение как граница применимости, не доказательство глобальной уникальности. Успех внутри одной контролируемой сессии. [Walkthrough](../architecture-review.md#повторная-аналитическая-проверка).

Уточнение ARCH-R-005: Clear определяется по совокупности принятых safety-входов ADR-0005. Пока хотя бы один не разрешён или есть отказ регистрации, нет обычного перехода даже с актуальной карточкой. Safety-only вход не является эпизодом, правкой или кандидатом; не переносится в запись/следующий эпизод. После Clear не исполняется ранее ожидавший Save; нужно новое явное подтверждение актуальной версии. Первичный ввод сохраняется в живой сессии; при инвалидированном разрешении до обычных действий с карточкой человек явно продолжает его обработку или отказывается от неё. Текст, доставленный во время Saving/SaveUncertain, также safety-only независимо от прежнего safety-состояния. Read-only сверка уже начатой операции не меняет safety-состояние.
