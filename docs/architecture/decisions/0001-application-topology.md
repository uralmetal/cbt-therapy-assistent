# ADR-0001: Топология приложения

**Статус:** Proposed · **Дата:** 2026-11-24 · **Готовность:** READY

**Лицо, принимающее решение:** заказчик. **Требования:** R1, R2, R3, R7, R8 ([реестр требований](../architecture-readiness.md)). **Зависимости:** нет; задаёт контекст ADR-0002–0006.

## Контекст и критерии

Один сценарий создания записи требует интерфейса, управления состоянием, вызова внешнего API из Python и сохранения. До учебного дедлайна 7 декабря нет подтверждённых требований к масштабированию, независимому релизу компонентов или высокодоступной инфраструктуре. Код проверяется преподавателем, поэтому бизнес-правила должны быть видны и проверяемы без внешней модели. Обязательные критерии: внешний API из Python, выполнение общих инвариантов и воспроизводимый запуск. Желательные: мало инфраструктуры, простота демонстрации и замены UI.

## Альтернативы

| Вариант | Проверяемость | Сложность и доставка | Ограничения |
|---|---|---|---|
| A. Notebook/один скрипт без границ | Возможна, но сценарий и вызовы переплетены | Низкий стартовый порог | Сложнее изолировать состояние и адаптировать интерфейс |
| B. Модульное Python-приложение в одном процессе | Ядро и адаптеры тестируются отдельно | Один релиз, минимум сетевых границ | Общий жизненный цикл UI и ядра |
| C. Отдельный веб-клиент и Python API | Хорошая изоляция, контрактное тестирование | Дополнительные сетевые ошибки, две конфигурации | Оправдано при независимых клиентах или отдельном API |

A не неприемлем сам по себе, если удаётся реализовать инварианты; обычный линейный notebook не даёт их автоматически. C также выполняет требования, но добавляет расходы без подтверждённого драйвера.

## Рекомендация архитектора

B: модульный монолит, в котором интерфейс вызывает сервис сценария в процессе, а ядро работает через ограниченные порты LLM и хранения. Это не предписание конкретного фреймворка. Интерфейс заменяем, бизнес-правила не живут в виджетах. Внешний API вызывается серверным Python, а не браузером. Для учебного запуска предпочтительна локальная воспроизводимая конфигурация; размещение на закрытом стенде допустимо при наличии подходящей среды и выполнении ADR-0004/0005 и Q09. Провайдер и площадка не выбираются этим ADR.

Уверенность высокая относительно границ компонентов, не относительно конкретного стека. Если появится обязательный независимый API, несколько клиентов или подтверждённые ограничения среды, сравнить B и C заново.

## Последствия и проверка

Плюс — один релиз и возможность тестировать ядро без UI/LLM. Минус — меньше независимости масштабирования; нужно дисциплинированно сохранять модульные границы. Проверка: один чистый запуск по инструкции; тест сценария с заглушками без сети; отдельно реальный вызов внешнего API с синтетикой и наблюдаемое сохранение. Критерий: UI не выполняет запись сам и не владеет бизнес-переходами; API-ключ не доступен браузеру. Доказательства ручных тестов — синтетические скриншоты/видео.
