# ADR-0001: Топология приложения

**Статус:** Accepted · **Дата:** 2026-11-24 · **Готовность:** READY

**Лицо, принимающее решение:** заказчик. **Требования:** R1–R8, R10–R12 ([Readiness](../architecture-readiness.md)). **Зависимости:** ADR-0002/0004/0006/0007; Q09 для допуска данных.

## Контекст и критерии

Заказчик явно задал Render, строго stateless Python, отсутствие локального хранилища, до 10 пользователей и ожидаемый поток менее 1 запроса/с. [Комментарий о Telegram + Python API](https://github.com/uralmetal/cbt-therapy-assistent/pull/3#discussion_r4677176362) — требование рассмотреть вариант, не выбор интерфейса. RPS — оценка входящего трафика, не SLA и не оценка месячного объёма. Общие инварианты СМЭР, учебный срок 07.12.2026 и воспроизводимость сохраняются.

## Альтернативы

| Вариант | Что развёртывается | Оценка |
|---|---|---|
| A. Notebook как основное приложение | Notebook и внешнее хранилище | Удобен для учебной демонстрации; сам по себе не удовлетворяет заданному хостингу приложения на Render |
| B. Модульный Python web UI | Один web service, UI и ядро, внешняя БД | Простой релиз; UI и сессии не могут быть источником истины; возможен Streamlit с внешним состоянием |
| C. Telegram + Python API | Telegram как внешний UI, один Render web service с webhook, ядром и адаптерами, внешняя БД | Нет отдельного frontend; естественный чат; доставка повторов, холодный старт и доступ требуют контроля |
| D. SPA + Python API | Отдельный frontend и backend | Полный контроль UI, дополнительные разработка и доставка; при текущей нагрузке не обязательны |

## Рекомендация архитектора

C принят заказчиком в связке с ADR-0006: **один модульный stateless Python HTTP-сервис** (FastAPI — кандидат) на Render, Telegram Bot API по HTTPS webhook, внешняя транзакционная БД, внешняя LLM. Это монолит с входным HTTP-адаптером, а не микросервисы и не отдельный API только ради архитектурного слоя. UI, оркестрация СМЭР, safety, хранилище, LLM — модули; один backend подходит также для B или D. Источник истины вне процесса: ни RAM, ни диск, ни UI-сессия не держат обязательное состояние между запросами; локальные временные переменные/пулы соединений допустимы только как заменимые технические ресурсы. Тестовый запуск локально подключается к изолированной внешней БД/заглушкам (не режим пользовательского хранения). Состояние, идентичность входов, идемпотентность, safety и незавершённые операции хранятся в единой внешней транзакционной системе. Не вводить Redis, очередь-брокер или отдельный сервис без подтверждённой необходимости; минимальный устойчивый inbox/реестр работ в той же БД описан в ADR-0002/0004.

Render Free Web Service — кандидат тарифа: 750 часов на workspace в месяц, сон после 15 минут без трафика, пробуждение может занять около минуты; файловая система эфемерна. Проверить остаток часов workspace и доступность внешних API. Webhook, а не постоянный polling или фоновый worker на бесплатном экземпляре. Не обещать мгновенную реакцию на холодном старте; при недопустимости задержки — согласовать платный always-on тариф, не обходить лимиты искусственным keepalive. Render выбран как площадка, не тариф. В [Render MCP](https://render.com/docs/mcp-server) и доступном коннекторе предусмотрен анализ логов/метрик и деплой; управление через ИИ не является частью пользовательского сценария, доступ ограничить, логи технические без текста, секретов/ID пользователей. Ссылки на политики и лимиты проверены 24.11.2026: [Render Free](https://render.com/docs/free), [Telegram Bot API](https://core.telegram.org/bots/api).

## Последствия и проверка

Плюс — привычный чат и один релиз; минусы — зависимость от Telegram и сети, ограничение редактирования сообщений и повторная доставка. Проверки: холодный старт, рестарт во время safety/Save, повтор webhook, два пользователя/две вкладки при альтернативном UI, изоляция, воспроизводимый запуск и фактическое внешнее API с синтетикой. UI не владеет состоянием и не выполняет запись; никакие токены/тексты не попадают в логи. Telegram выбран; FastAPI — технический кандидат, смена интерфейса потребует пересмотра ADR.

## Решение заказчика

24.11.2026 · [Комментарий](https://github.com/uralmetal/cbt-therapy-assistent/pull/3#discussion_r4677547656) на HEAD `a1b6d2ee01ea71ea8ef8432989c22297a52e0f34`.

Принят вариант C: Telegram + один модульный stateless Python HTTP-сервис на Render, внешняя БД и LLM. FastAPI остаётся рекомендованным фреймворком, тариф Render — условным. Варианты A/B/D сохранены как история сравнения.

Принятие решения не равно готовности реализации. Условия, проверки и открытые вопросы остаются в силе; фактические тесты не выполнены.
