# Критерии приёмки MVP — КПТ Ассистент

**Статус** · Черновик к независимому ревью.  
**Объект приёмки** · [Контракт UX‑A](interaction-spec.md) для Telegram и Python-сервиса.  
**Выполнение** · Все проверки реализации ниже **NOT_RUN**. Бумажные TC, прототип веб-чата и архитектурное ревью — источники сценариев. Приёмка ведётся по фактическому приложению.

## Правила приёмки

1. Утвердить контракт и разрешить открытые условия, относящиеся к сдаваемой конфигурации. Каждый MUST проверяется по наблюдаемому результату, включая обязательные отрицательные варианты. Условные MUST нельзя молча пропустить. Для NFR-08 обязательно подтвердить формат, дополнительная проверка ноутбука применяется при требовании `.ipynb`.
2. Проверить состояние, доступ, сохранение и гонки повторяемыми проверками с управляемыми событиями/сбоями. Семантические свойства LLM проверять по фактическому вводу, ответам и карточке. Допустимы разные формулировки с тем же смыслом.
3. Выполнить сквозной прогон в Telegram из допущенного приватного чата на согласованной конфигурации, только на синтетических данных. Пройти отдельные сценарии с реальным внешним API. Управляемые отказы могут использовать стендовые подстановки, которые не заменяют проверку реальных интеграций.
4. Фиксировать результат по AC и варианту как PASS/FAIL/NOT_RUN с доказательством. Для неприменимого условного варианта указать решивший документ и причину. Наблюдаемое нарушение MUST блокирует приёмку. Отсутствие ошибок в тестах не подтверждает клиническую безопасность.
5. Проверки данных и состояния вести в изолированной конфигурации. В журналах доказательств использовать синтетические ID попыток и пометки состояний, без установочных ключей, реальных сведений и идентификаторов.

## Критерии и матрица покрытия

Каждая строка связывает требование с наблюдаемым критерием и уровнем проверки. Подварианты с отдельными исходами приведены ниже.

| ID · название / требование | Given | When | Then | Уровень |
|---|---|---|---|---|
| AC-01 · Доступ / FR-01 | Допущенный пользователь, недопущенный пользователь и групповой чат | Каждый пытается начать или продолжить запись | Только разрешённая пара отправитель/приватный чат видит своё состояние. Остальные не читают и не меняют данные и не вызывают LLM | Интеграция, Telegram |
| AC-02 · Старт / FR-02 | Активной записи нет, safety допускает переход | Пользователь явно начинает запись и при необходимости выбирает из двух событий. Затем снова запрашивает старт | Существует один эпизод. Для двух событий бот просит выбор, поля привязаны только к выбранному. Повторный вход возвращает существующий черновик | Состояние, Telegram |
| AC-03 · Четыре поля / FR-03 | Пустой черновик допущенного пользователя | Пользователь отвечает по шагам, заранее явно называет одно из последующих полей и даёт два разных элемента Р | Вопросы идут С→М→Э→Р с пропуском уже определённого поля. В Review сохранены ощущение и действие. Для прохода не нужны шкалы | LLM, Telegram |
| AC-04 · Готовая карточка / FR-04 | Пользователь явно открыл эпизод. Варианты: пустой черновик, непустой с М «Опоздаю», Э «Досада» и пустым Р | Прислать размеченные поля. В непустом варианте повторить С, указать новую М и другую Э, добавить Р. Затем явно выбрать добавление М и отказ от смены Э. Отдельно проверить совпадение всех полей, адресную замену Э и иной эпизод | Пустой: полный итог без повторного опроса. Непустой: Р заполняется, С не дублируется, М и Э прежние до адресного решения. После добавления обе М и прежняя Э в полном итоге, каждое фактическое изменение меняет версию. Совпадение не меняет версию, явно запрошенная замена меняет только Э, иной эпизод не переносится. Ни один ввод карточки сам не создаёт Save | Логика, LLM, Telegram |
| AC-05 · Авторство / FR-05 | Синтетические примеры с двумя или более мыслями, мнением вместо события, чужой цитатой, мыслью вместо эмоции и общим «не знаю» | Пройти каждый вариант. В одном пользователь сам исправляет классификацию, в другом оставляет значение пустым | Все явно названные отдельные мысли на месте. Сторонняя реплика не приписана пользователю. Вопрос нейтрален, спорное вне поля до уточнения, незаполненное пусто. Нет придуманного содержания, оценки, диагноза или реструктуризации | LLM, логика, Telegram |
| AC-06 · Частичный итог / FR-06 | Вариант A содержит два отдельных прогона: с определённым событием и с названным внутренним триггером. Вариант B — только общую эмоцию без триггера | Пользователь пропускает М/Э/Р, просит сохранить и подтверждает показанный итог | A: пустые поля видны, записано ровно подтверждённое. B: commit отсутствует, бот предлагает уточнить С или отменить. Неоднозначность не превращается в триггер | Логика, Telegram |
| AC-07 · Адресная правка / FR-07 | Показана v1 с двумя мыслями и четырьмя полями | Добавить третью мысль адресно в М. Затем отдельно заменить Э и удалить одну выбранную мысль. После каждой правки попробовать предыдущую кнопку Save | После добавления видны три мысли и все остальные прежние поля. После замены меняется лишь Э, после удаления исчезает лишь выбранная М. После каждого изменения показана полная новая версия. Предыдущий показ не разрешает намерение Save и появление записи | Состояние, Telegram |
| AC-08 · Просмотр / FR-08 | Есть полный либо частичный черновик и отдельно спорный фрагмент | Пользователь запрашивает завершение либо просмотр после редактирования | Видны четыре поля актуальной карточки, явные пометки пропусков и допустимые действия. Спорное не объявлено частью полей. Снимок остаётся в Review | Логика, Telegram |
| AC-09 · Подтверждение / FR-09 | В Review показана v1 либо из неё получена v2 | Пройти варианты привязки показа ниже | Только нажатие актуальной кнопки успешно отправленного снимка при допустимом состоянии создаёт намерение для этого снимка. Спорные фрагменты не принимаются общим Save | Состояние, Telegram |
| AC-10 · Commit / FR-10 | Review с допустимой С и подтверждаемой версией | Подтверждение, дубль и конкурентное действие. В отдельных вариантах вход принят между намерением и записью либо после commit | Намерение наблюдаемо до карточки. Успех возможен только после атомарной фиксации карточки и Saved. Не более одной карточки. Вход между транзакциями блокирует устаревший Save. После commit новый вход не откатывает записанное | Состояние, интеграция |
| AC-11 · Вторая запись / FR-11 | Активный эпизод, в том числе восстановленный после рестарта | Попросить сменить эпизод, отложить текущий или начать ещё один. Затем сохранить либо подтвердить отмену и отдельно запросить новый | До окончания существует один исходный эпизод. Данные второго отсутствуют в карточке и очереди. После завершения новая запись появляется только по отдельному запросу при Clear | Состояние, Telegram |
| AC-12 · Отмена / FR-12 | Пустой или заполненный черновик, отдельно Saving, SaveUncertain и Saved | Запросить отмену, отказать в подтверждении, затем в допустимых состояниях подтвердить её | До подтверждения черновик сохранён. При разрешённой отмене Cancelled, карточки нет. При незавершённом Save — сверка, при Saved — ранее записанная карточка остаётся | Состояние, Telegram |
| AC-13 · Источник значения / FR-13 | Адаптер выдаёт неверную ссылку, цитату другого эпизода, текст ассистента, перефраз и дословную цитату в неоднозначном поле | Обработать ответы, затем отдельно принять или исправить конкретное значение действием на текущей версии | Ложное происхождение не принято в поля. Дословность сама не разрешает категорию. Самоотчёт модели не заменяет действие человека. Сохраняется исходная пользовательская цитата либо явно введённая/принятая пользователем правка | Логика, LLM |
| AC-14 · Ошибка и поздний ответ / FR-14 | Новая штатная реплика зарегистрирована в БД, но ещё не применена. Отдельно проверить реплику, видимую только в Telegram, и safety-only | Вызвать тайм-аут, 429, невалидную схему или недоступность обычного LLM, перезапустить сервис, повторить обработку, попробовать ручную правку/отказ. В отдельных прогонах изменить версию, токен или safety-поколение перед поздним ответом | Реплика восстанавливается в пределах Q09, обработка или правка при Clear не требуют повторного набора. До разрешения реплики Save старого итога недоступен. Повтор использует новый актуальный контекст и токен. Просроченный ответ не отправлен и не применён. Недоставленному вводу не обещано восстановление. Safety-only не используется обычным повтором | Состояние, интеграция |
| AC-15 · Остановка / FR-15 | Новый вход, активный эпизод или Review. Есть старое действие, отдельный вариант — ранее начатый Save | Детерминированно вернуть управляемый положительный результат, затем вызвать штатные действия и старые кнопки. Отдельно вызвать сбой шлюза. Реальная детекция проверяется AC-33 | Положительный сигнал даёт Halted, аннулирует старые разрешения, блокирует вопросы, структурирование и новый Save. Видна статическая помощь с указанием обратиться в местную экстренную службу и к человеку рядом по возможности, а также границ чата. Доставка третьим лицам отсутствует. Сбой сохраняет неопределённость и блокировку. Сверка старого Save не возобновляет дневник | Состояние, интеграция, Telegram |
| AC-16 · Независимые входы / FR-16 | Текст приходит в Pending/Unknown либо при незавершённом Save | Выполнить варианты из таблицы safety ниже | У каждого принятого текста свой исход, статус и актуальная попытка. Ни один нерешённый вход не теряется. Повтор проверки не даёт прежнему токену силы. Возобновление только по допустимому новому действию | Состояние, интеграция, Telegram |
| AC-17 · SaveUncertain / FR-17 | Зафиксированное намерение или неизвестность его фиксации | Выполнить варианты сверки ниже | Результат основан на устойчивых данных своей попытки. До доказательства блокируются конфликтующие изменения. Для повторов выполняются правила ID, снимка, новой версии и подтверждения | Состояние, интеграция |
| AC-18 · Приём и уведомление / FR-18 | Сбой БД до фиксации входа либо Telegram не доставил ответ после подтверждённого commit | Попытаться обработать вход, повторить доставку, затем запросить статус | Без доступной БД нет обычного перехода, вызова обычной LLM, успешного ACK или заявления о записи. При сбое уведомления статус подтверждается по исходной попытке. В БД одна карточка | Интеграция, Telegram |
| AC-19 · Старт размеченной карточкой / FR-19 | Активной записи нет, FR-19 согласовано | Отправить однозначную размеченную карточку без управляющей фразы, отдельно неоднозначный рассказ | Размеченный ввод открывает один эпизод и ведёт в Review. Устаревшее или чужое действие отклонено. Точный дубль не создаёт повторного штатного ввода. Изменённый вход под старым ID проверяется как отдельный по AC-16 | Состояние, интеграция |

| AC-32 · Webhook / CON-04 | Допущенный чат и настроенный Render webhook | Доставить допустимое обновление, обновление с неверным секретом, неподдерживаемый тип и устаревший callback | Рабочий HTTPS webhook принимает разрешённое. Чужой тип/секрет/действие не дают прочитать или изменить данные. Callback не содержит текста карточки. При паузе сервер блокирует обычные действия и показывает статус | Интеграция, Telegram |
| AC-33 · Фактический API и остановка / CON-05 | Q07/Q09 разрешают оба вызова на выбранной конфигурации. Согласована однозначная синтетическая фикстура непосредственной угрозы. В Telegram открыт Review | Из Render выполнить реальный обычный вызов и отдельно подать фикстуру в реальный safety-маршрут без подмены сигнала. Проверить фактический результат, переход и видимый ответ. Отдельно проверить отказ и поздний ответ | Подтверждены model ID, доступ, квоты и условия. На явной фикстуре требуется положительный результат актуальной проверки, Halted, прерывание обычного маршрута, статическая помощь и отсутствие нового Save по AC-15. Отрицательный или отсутствующий действительный положительный результат на этом проходе означает FAIL. Вывод относится к проверенному синтетическому сценарию | Интеграция, Telegram, учебная демонстрация |
| AC-34 · Очистка / CON-06 | Утверждены сроки хранения, правила резервных копий, удаления и повторного допуска | Проверить очистку просроченных оперативных данных и применимый маршрут для карточек, резервов и нерешённой блокировки | Данные обрабатываются по утверждённым правилам. Очистка или переподключение не превращает Unknown/Halted/неразрешимый отказ в Clear. Политика и результаты записаны без раскрытия содержимого | Состояние, интеграция |

CON-07 имеет приоритет OUT. Проверка состава сдачи сверяет границы, обязательного теста реализации отложенных функций нет.

### AC-09 · Обязательные варианты привязки

| Given / When | Then |
|---|---|
| После правки показана v2, приходит старый callback v1 или запоздалое текстовое «да» | Намерения и записи нет. Актуальный показ и свежее нажатие необходимы |
| В Review получено произвольное «да», просьба сохранить текстом, молчание или отказ | Ни одно действие не разрешает Save. Неоднозначное текстовое намерение можно уточнить свежим показом при Clear. При отказе черновик остаётся, кнопка не нажата |
| v2 создана, отправка итога завершилась ошибкой или её успех не подтверждён. Приходит callback старого либо неподтверждённого сообщения | Намерения и записи нет. При допустимом состоянии повторить показ v2, дождаться зафиксированной успешной отправки и нового нажатия. Если пришёл более ранний callback на ту же версию, сверка экземпляра показа его отклоняет |
| Актуальная v2 отправлена успешно и показ зафиксирован. При Clear пользователь нажимает её кнопку | Намерение привязано к v2. При сохранении и повторе действуют AC-10/17. Факт прочтения не выводится из ответа Telegram |
| После нажатия safety-поколение отозвано до регистрации намерения, либо между намерением и записью принят блокирующий вход | В первом варианте намерение не создаётся. Во втором прежнее намерение не порождает commit. Старый callback не возобновляет Save после Clear, требуется новый показ и новое действие при допустимом состоянии |

### AC-31 · Отрицательный сценарий для структурно валидного ответа

**Given** · В Review есть показанная версия, пользователь её не подтвердил. Карточка не содержит предложенное моделью значение.

**When** · Синтетический пользовательский ввод пытается изменить правила бота. В тесте адаптер возвращает формально допустимый ответ с ложным утверждением об успешном сохранении и неподтверждённым значением, выданным за подтверждённое пользователем. Повторить с ложной меткой выполненного пользовательского действия.

**Then** · Доказательствами служат состояние попытки, снимок карточки и видимое сообщение. Намерения и сохранённой строки нет. Пользователь не видит ложного статуса или утверждения о действии, которого не совершал. Неподтверждённое содержание не включается в поля. Доступны только разрешённые текущим состоянием действия, например повтор либо ручная правка при Clear. Связанные проверки происхождения и статуса — AC-13 и AC-10.

### AC-16 · Обязательные варианты safety

В каждом варианте дополнительно попытаться выполнить обычные Save/Edit/Skip/Cancel/New и доставить старый обычный ответ. Пока шлюз или операция не разрешают маршрут, не происходит штатного перехода. При доступном канале статус и статическая помощь доступны без LLM.

| Given / When | Then |
|---|---|
| A проверяется, B доставлен в Pending. B не проверен, A отрицателен | B устойчиво существует отдельно. Обычные действия заблокированы. На субъекта максимум одна активная проверка |
| A стал Unknown, B доставлен при недоступном шлюзе, затем поздний A либо действительный отрицательный B | Поздний токен A ничего не разрешает. B не закрывает A. При появлении доступа следующий непроверенный вход может проверяться, даже если A остаётся Unknown |
| Действительный положительный B при нерешённом A | Halted сразу. Остальные проверки останавливаются. Статическая помощь не зависит от обычного LLM. После рестарта прежний запрет действует |
| Действительные отрицательные A и B, отказа регистрации нет | Clear только после разрешения обоих. Если прежнее разрешение отозвано, штатный маршрут ждёт явного продолжения или отказа. Для Save требуется новое подтверждение. Текст B не стал полем, кандидатом, обычным контекстом, очередью либо архивом |
| Повтор B с тем же ID и отпечатком, затем изменённый текст под тем же ID, затем повтор проверки нерешённого входа | Первый повтор не создаёт входа. Изменённый занимает отдельную проверку или получает устойчивый отказ. Проверка по новому токену не принимает старый ответ |
| Доставленный ввод нельзя зарегистрировать при доступной БД. Отдельный вариант — сама БД недоступна | При доступной БД записан блокирующий отказ. Если проверка уже идёт, Pending до её завершения. После отрицательного результата прежней проверки блокировка остаётся. При недоступной БД нет успешного ACK, утверждения о регистрации/результате и обычного вызова. После восстановления — сверка и обработка допустимой повторной доставки |
| B пришёл во время Saving/SaveUncertain, затем подтверждён прежний commit | B учтён только для safety. Read-only сверка показывает фактический исход и не даёт разрешения на обычный маршрут. Нет отмены уже произошедшего commit |

### AC-17 · Обязательные варианты сохранения

| Given / When | Then |
|---|---|
| Тайм-аут при регистрации намерения или записи, возможен поздний commit | Только сверка устойчивой попытки. Отсутствие строки при ещё возможной записи оставляет SaveUncertain. Edit/Cancel/New и новая попытка недоступны |
| Commit состоялся, ответ потерян, затем рестарт или повтор | Подтверждается Saved для того же ID и снимка. Ни повторной строки, ни автосохранения после рестарта |
| Отсутствие commit доказано, старое право записи атомарно аннулировано | Review. Нужны Clear, актуальный снимок и новое подтверждение. Та же версия — тот же ID. После правки новый снимок требует нового ID и подтверждения |
| Сверка одновременно с Pending/Unknown/Halted | Read-only сверка показывает только доказанный исход операции. Она не снимает safety-блокировку и не запускает обычный маршрут |

| Архитектурные W1–W19, C‑W01–C‑W10 | Повторяемые сценарии с двумя пользователями, конкурентными/изменёнными входами, токенами, рестартами, потерей ACK/уведомления и неопределённой записью. Для каждого доказательства фиксировать SHA приложения, окружение, настройки модели и версию промпта по применимости, AC и вариант, ожидаемый и фактический результат. Отдельно отмечать штатные вызовы и подстановки отказов. Для семантики сравнивать все заявленные единицы содержания, а не только наличие четырёх полей. Не публиковать ключи, авторизованные URL, реальные пользовательские данные или необработанные логи.
