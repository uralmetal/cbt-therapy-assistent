## Prompt Prototype

Пройдены Product Discovery и независимое ревью шести диалогов. men-iun реализовал последовательный UX‑A в ChatGPT. Заказчик выбрал его как самый простой и наименее рискованный для MVP. UX‑B отклонён по методологическим причинам: мысли, эмоции, ситуацию и реакции определяет человек. UX‑C не удалось реализовать и протестировать. В UX‑A показан короткий путь для опытного пользователя, который уже сформулировал С, М, Э и Р. Вывод относится к наблюдавшемуся поведению прототипа. MVP требует показать актуальную карточку и получить отдельное подтверждение при закрытии. Этап завершён, повторная реализация не нужна. [Резолюция UX‑A](https://github.com/uralmetal/cbt-therapy-assistent/pull/2#issuecomment-7197733095) · [Решение по UX‑B](https://github.com/uralmetal/cbt-therapy-assistent/pull/2#issuecomment-7197797120) · [Ревью UX‑A](../product/manual-ux-a.test.md) · [Протокол UX‑C](../product/manual-ux-c.test.md)

## API Prototype

A реализует Telegram Bot API, B — Gemini API, системный промпт и контекст. Тимлид владеет точкой входа и контрактом. Синхронность и память процесса действуют только в прототипе. Этап закрывается общим ручным прогоном локального Telegram → реальный Gemini → Telegram на разрешённой синтетике, показом карточки UX‑A, проверкой сохранения контекста между репликами и изоляции двух пользователей. [Интеграционный контракт и чек-лист](api-prototype.md) · [Порядок рабочих PR](git-workflow.md)

[PR #2](https://github.com/uralmetal/cbt-therapy-assistent/pull/2) собирает Discovery, Prompt Prototype, требования, архитектуру и план со скелетом. API Prototype, Functional MVP и Release получают по одному отдельному итоговому PR в `main`, каждый от результата предыдущего этапа. У API Prototype два рабочих PR сходятся в интеграционную ветку.

**Завершение Functional MVP.** Итоговый PR содержит рабочий код и проверяемые результаты обязательных AC. В автоматизированный минимум входят переходы карточки, ограничения LLM, сбои/рестарт, конкуренция, изоляция, Save и блокировки safety. Статусы приёмки отражают фактические проверки. Блокирующий обязательный критерий оставляет этап незавершённым.

**Definition of Done.** Тимлид принимает релизный PR после независимого ревью. Обязательная приёмка закрыта результатами актуальной версии. Код и конфигурация запуска воспроизводимы. В описании сдачи явно выделены название проекта, практическая задача, цель, целевая аудитория и сценарий использования. Репозиторий согласован как формат сдачи по O‑04.
